## 1. 产品概述

**背景**：本项目是《软件项目管理》课程的统一命题作业，全班各组均围绕"错题本系统"进行设计与实现，架构与技术栈自主选择。

**产品定位**：面向备考学习者的个人错题管理工具。核心价值是通过"拍照录入 + OCR 自动识别"降低记录错题的门槛，并通过学科/知识点分类与掌握状态标记，帮助用户在考前高效聚焦薄弱环节、反复巩固。

## 2. 目标用户与使用场景

### 2.1 用户画像

- **主要用户**：正在备考的学习者，不限定具体学段或考试类型（可以是中学生的日常测验/月考，也可以是成人备考资格考试、外语考试等）。
- **核心诉求**：把做题过程中暴露的错误集中记录下来，避免遗漏，并能在考前反复回顾，强化薄弱知识点。
- **使用环境**：个人独立使用，不涉及班级/教师协同；本阶段不做账号体系，单机使用。

### 2.2 核心使用场景

1. 用户完成一次练习/试卷后，翻看批改结果，找到做错的题目。
2. 打开错题本系统，拍照上传错题图片。
3. 系统通过 OCR 识别图片中的文字，自动生成题目内容草稿。
4. 用户核对、修改 OCR 识别结果，并补充学科、知识点标签、错误原因等信息后保存。
5. 错题进入错题库，可按学科、标签、时间等维度筛选查看。
6. 复习时，用户逐条查看错题，把已经理解掌握的题目标记为"已掌握"，未掌握的题目保留在待复习列表中。

### 2.3 用户故事

- 作为一名备考学习者，我希望能拍照快速录入错题，而不必手动打字，这样记录错题的门槛更低，我更愿意坚持使用。
- 作为一名备考学习者，我希望 OCR 识别有误时能方便地手动修改，因为图片识别不可能 100% 准确。
- 作为一名备考学习者，我希望能给错题打学科/知识点标签，以便按知识点复习。
- 作为一名备考学习者，我希望能标记错题是否"已掌握"，以便下次复习时优先看还没掌握的题目。

### 2.4 后续迭代方向（暂不在本阶段范围内，先记录以备后续规划）

- 接入 VLM + LLM：自动判断学科/知识点、自动生成错题解析或讲解、辅助分析错误原因。
- 复习强化功能：如生成复习计划、随机抽题自测、遗忘曲线提醒等。
- 多用户/账号体系（如未来扩展到班级场景）。

## 3. 范围定义

### 3.1 本阶段做（In Scope）

- 错题拍照上传，OCR 自动识别文字生成题目草稿
- 错题信息手动核对/编辑（题目内容、答案、学科、知识点标签、错误原因）后保存
- 按学科、标签、时间浏览、筛选、关键字搜索错题
- 查看错题详情（含原始图片）
- 标记错题"已掌握 / 未掌握"
- 错题的编辑与删除
- 学科 / 知识点标签的新建与管理

### 3.2 本阶段明确不做（Out of Scope）

- 账号体系与多用户数据隔离（单机使用）
- 接入 VLM + LLM 的智能解析、自动知识点识别、自动生成讲解
- 复习计划生成、随机抽题自测、遗忘曲线提醒等复习强化功能
- 教师 / 班级协同功能
- 移动端原生 App（仅 Web，适配移动浏览器）

## 4. 功能需求

优先级说明：**P0** = 本阶段必须交付；**P1** = 有余力再做；**P2** = 可选加分项。

| 编号 | 功能                 | 优先级 | 说明                                                             | 验收标准                                                                     |
| :--- | :------------------- | :----- | :--------------------------------------------------------------- | :--------------------------------------------------------------------------- |
| F1   | 拍照上传 + OCR 识别  | P0     | 用户拍照或上传图片，系统调用 OCR 识别文字并自动填充题目内容草稿  | 清晰图片下能生成可读的文字草稿；识别失败时给出提示并允许手动输入，不阻断流程 |
| F2   | 错题信息编辑与保存   | P0     | 编辑/补充题目内容、正确答案、学科、知识点标签、错误原因          | 题目内容与学科为必填项，缺失时阻止保存并提示；保存成功后错题出现在列表中     |
| F3   | 错题列表与筛选       | P0     | 列表按时间倒序展示，支持按学科/标签/掌握状态筛选，支持关键字搜索 | 筛选与搜索结果准确且与实际数据一致                                           |
| F4   | 错题详情查看         | P0     | 展示完整题目内容、原始图片、答案、标签、掌握状态、时间信息       | 所有已保存字段均可在详情页查看                                               |
| F5   | 掌握状态标记         | P0     | 在列表或详情页将错题标记为"已掌握/未掌握"                        | 状态变更即时生效，并可作为筛选条件                                           |
| F6   | 错题编辑与删除       | P1     | 对已保存错题二次编辑或删除                                       | 编辑后列表/详情同步更新；删除前二次确认，删除后不可再查询到                  |
| F7   | 学科 / 标签管理      | P1     | 新建、编辑、删除学科分类与知识点标签                             | 删除标签后，已关联该标签的错题不报错（标签置空或提示需先解除关联）           |
| F8   | 错题导出（复习清单） | P2     | 按筛选条件导出错题为可打印的复习清单（如 PDF/图片）              | 可选功能，不影响核心链路交付                                                 |

## 5. 非功能需求

- **性能**：核心接口（列表、详情、保存）响应时间 ≤ 2 秒；OCR 识别属耗时操作，需有加载态反馈，避免用户误以为卡死。
- **可用性**：拍照上传到生成草稿的操作流程不超过 3 步；页面需适配移动端浏览器（响应式布局），便于用户直接用手机拍照录入。
- **可靠性**：错题数据持久化存储，服务重启或异常退出不丢失已保存数据；上传的原始图片需妥善保存并可追溯。
- **兼容性**：支持 Chrome / Edge / Safari 等主流现代浏览器最新版本。
- **可维护性**：前后端分离，接口具备基本的输入校验与统一错误提示，便于后续迭代扩展（如接入账号体系、VLM 智能解析）而无需推翻现有功能结构。

## 6. 迭代计划与里程碑

> 具体日期以班级课程进度表为准，此处按相对迭代周期规划。

- **迭代 1（第 1~2 周）**：跑通"拍照上传 → OCR 识别 → 手动核对保存 → 列表展示"最小闭环（F1、F2、F3、F4 的基础版本）。
- **迭代 2（第 3~4 周）**：完善筛选/搜索、学科与标签管理、掌握状态标记（F3 完整版、F5、F7）。
- **迭代 3（第 5~6 周，如排期允许）**：补齐编辑/删除（F6），打磨交互体验，并为下一阶段（VLM 智能解析、复习强化功能）预留扩展空间。

每次迭代结束参加班级排位赛评比，优先保证 P0 功能可运行、可演示。

## 7. 风险与假设

### 7.1 风险

| 风险                                                       | 影响                                         | 应对措施                                                               |
| :--------------------------------------------------------- | :------------------------------------------- | :--------------------------------------------------------------------- |
| OCR 识别准确率不稳定（手写字迹、公式符号识别效果可能较差） | 影响录入体验，可能打断使用流程               | 保留便捷的手动编辑修正入口，OCR 失败不阻断保存流程                     |
| 核心开发集中在个人一人                                     | 若遇学业/时间冲突，交付进度受影响            | 功能模块化拆分，明确接口边界，便于必要时其他组员补位；严格按优先级交付 |
| 每两周一次排位赛，节奏紧张                                 | 若某次核心功能未完成，直接影响当次评分       | 每个迭代只承诺 P0 范围，P1/P2 视余力弹性完成，避免"求全而不可用"       |
| 单机无账号的假设可能与后续规划冲突                         | 若后续要接入多端同步或账号体系，可能需要返工 | 提前在风险登记中标注，后续迭代规划设计时预留可扩展空间                 |

### 7.2 假设

- 假设错题图片来源为用户自行拍摄的纸质试卷/作业，图像总体清晰可辨，非极端模糊或倾斜场景。
- 假设排位赛评审关注"可运行的真实交互"，因此 MVP 需保证核心链路完整可演示，而非停留在原型或静态页面阶段。
