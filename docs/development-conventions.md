# 错题本系统 开发规范

> 状态：v0.1 ｜ 日期：2026-10-03
> 规则用 **必须** / **禁止** 表示强制要求，用 **应当** 表示默认做法、有理由可例外。
> 本规范是[项目宪法](../.specify/memory/constitution.md)的展开：两者冲突时以宪法为准，并立即修正本规范。

## 1. 接口响应规范

### 1.1 统一响应结构

**每个接口都必须返回下面的结构，并且 `code` 必须与 HTTP 状态码相同：**

```json
{ "code": 200, "message": "ok", "data": null }
```

| 字段 | 类型 | 规则 |
| :--- | :--- | :--- |
| `code` | int | 必须等于 HTTP 状态码，不得自造业务码 |
| `message` | string | 成功固定 `ok`（200）或 `created`（201）；失败是面向用户的中文提示，一句话，不含堆栈、SQL、文件路径 |
| `data` | object / array / null | 成功时是业务数据；失败时是错误详情，没有则为 `null`；**必须**始终存在，不得省略 |

- 禁止用"HTTP 200 + `code` 非 200"表示失败。
- 禁止在统一结构之外再加顶层字段。需要新增时先改本文档。
- 空结果也要返回结构：列表为空时 `data.items` 是 `[]`，删除成功时 `data` 是 `null`。

### 1.2 状态码

| code | 使用场景 |
| :--- | :--- |
| 200 | 查询、更新、删除成功 |
| 201 | 创建成功（POST 新建资源、上传） |
| 400 | 请求无法解析：JSON 格式错误、缺少文件字段 |
| 404 | 资源不存在；路由不存在 |
| 405 | 方法不允许 |
| 409 | 与现有数据冲突（唯一约束、仍被引用） |
| 413 | 上传内容超过大小上限 |
| 415 | 上传的文件类型不受支持 |
| 422 | 字段缺失、类型不对、取值不合法、业务校验未通过 |
| 500 | 未预期错误 |

- 校验类错误统一用 422，不要混用 400。400 只用于连请求都解析不了的情况。
- 新增状态码前先更新本表。

### 1.3 校验失败的 `data`

```json
{
  "code": 422,
  "message": "题目内容不能为空",
  "data": { "fields": [{ "field": "content", "message": "不能为空" }] }
}
```

- `message` 取第一条字段错误，写成用户能读懂的中文。
- `fields[].field` 是请求体里的字段名（`snake_case`）。

### 1.4 未预期错误

- 所有未捕获的异常由全局处理器转成 `{"code": 500, "message": "服务器开小差了，请稍后再试", "data": null}`。
- 完整堆栈只写日志，禁止返回给客户端。
- 路由不存在、方法不允许等框架自带的错误，也必须经处理器转成统一结构。

### 1.5 例外

- `GET /api/images/{image_id}` 成功时返回图片二进制，`Content-Type` 为图片类型；失败时返回统一结构。
- 除此以外**不允许**有第二个例外。

## 2. 接口设计规范

- 路径以 `/api` 开头，资源用复数名词：`/api/mistakes`、`/api/subjects`。路径中不出现动词，状态变更用子资源，如 `PUT /api/mistakes/{id}/mastered`。
- JSON 字段一律 `snake_case`。
- 时间一律 ISO 8601 UTC，带 `Z` 后缀：`2026-10-03T08:30:00Z`（可含小数秒）。数据库也存 UTC；SQLite 不保存时区，必须通过 `UtcDateTime` 类型读写，禁止直接用 `DateTime`。
- ID 对外是数据库整数；图片 ID 是 32 位十六进制字符串。
- 列表接口必须分页：`page`（从 1 开始，默认 1）、`page_size`（默认 20，最大 100）。`data` 为 `{items, total, page, page_size}`。越界的 `page` 返回空 `items`，不报错。
- 例外：数量有限的小集合（学科、标签）可以不分页，`data` 为 `{items: [...]}`。增长不受限的数据（错题）必须分页。
- 列表排序必须稳定：先按业务字段，再按 `id` 兜底。
- 请求和响应都用 Pydantic 模型声明，禁止在路由里直接读写 `dict`。
- 路由里只做：解析请求 → 调用 service → 包装响应。业务规则放在 service。

## 3. 后端代码规范

### 3.1 分层与依赖方向

```
api  →  services  →  models / ocr
```

- `services` **禁止** import `fastapi`；它通过抛出 `AppError` 的子类表达失败。
- `api` **禁止**直接操作数据库会话做业务判断。
- 业务代码**禁止** import 具体 OCR 库，只依赖 `ocr.base.OcrEngine`。
- 依赖（数据库会话、OCR 引擎、配置、时钟）通过 FastAPI 依赖注入或函数参数传入，**禁止**在函数内部直接读全局单例，否则无法测试。

### 3.2 错误处理

- 业务错误统一抛 `app.errors.AppError` 的子类（`NotFoundError`、`ConflictError`、`ValidationFailed` 等），每个子类固定一个 `code`，等于 HTTP 状态码。
- 只在全局处理器里把 `AppError` 转成响应。路由里**禁止**手写 `JSONResponse` 拼错误。
- 禁止吞掉异常：`except Exception: pass` 不允许。唯一例外是 OCR 适配器，它要把引擎异常转为 `OcrResult(status="failed")`，并且必须记录日志。

### 3.3 风格

- 必须通过 `ruff check` 和 `ruff format --check`，行宽 100。
- 公共函数、方法必须有类型标注。
- 命名：模块与函数 `snake_case`，类 `PascalCase`，常量 `UPPER_SNAKE`。
- 注释写"为什么"，不写"做了什么"。中文注释即可。不要写会随代码变旧的注释。
- 不留无用代码、`print` 调试和注释掉的代码。日志用 `logging`。

### 3.4 配置

- 所有可变配置来自环境变量，在 `config.py` 统一定义（`pydantic-settings`），带默认值。
- 新增环境变量时，同时写入 `backend/.env.example` 并加到 `config.py`。
- 禁止把密钥、绝对路径写进代码或提交到仓库。

### 3.5 数据库

- 外键、唯一性、非空约束写在表结构里，不只靠应用层校验。
- **表结构变更必须有版本**（宪法 v1.1.0）：用 Alembic 管理，每次变更新增一个迁移文件，随代码一起提交；数据库里记录当前版本。
  **禁止**靠 `create_all` 修改已存在的表，禁止手工改库。
- 每个迁移必须有测试：①从上一版本升级后数据不丢；②升级到最新后的表结构与 ORM 模型一致（改了模型忘写迁移，这个测试会失败）。
- 应用启动时：库没有版本记录 → 登记为基线版本 `0001`（迭代 1 的表结构）；库版本低于代码 → 自动升级；库版本高于代码 → 拒绝启动并说明原因。
- 删除有被引用关系的数据，要么级联、要么拒绝（409），不得留下悬空引用。

## 4. 面向对象设计规范

类用来表达两种东西：**带依赖的行为单元**（service）和**可替换的实现**（OCR 引擎）。不为了用类而用类。

### 4.1 Service 类

- 每个业务领域一个 service 类：`SubjectService`、`ImageService`、`UploadService`、`MistakeService`。
- 依赖（`Session`、`OcrEngine`、时钟、数据目录）**必须**通过构造函数注入，保存为私有属性（`self._session`），**禁止**在方法里读全局变量或自己创建依赖。
- 方法对应一个业务用例，名字用动词：`create`、`list_all`、`get`、`save`。一个方法只做一件事。
- service 实例**按请求创建**（由 FastAPI 依赖注入提供），不得保存跨请求的可变状态。
- 公共方法超过 10 个时，说明职责过多，拆成两个类。

```python
class SubjectService:
    def __init__(self, session: Session) -> None:
        self._session = session

    def create(self, name: str) -> Subject: ...
```

### 4.2 接口与适配器

- 外部能力（OCR、时钟、文件存储）用 `typing.Protocol` 定义接口，接口定义在**使用方**所在的包里（`ocr/base.py`），实现类放在同一个包里。
- service 只依赖接口，**禁止** import 具体实现。换引擎只新增一个实现类，不改 service（开闭原则）。
- 任何实现都必须遵守接口契约，保证可互换（里氏替换）：例如 `OcrEngine.recognize` 不得向外抛异常，失败返回 `OcrResult(status="failed")`。
- 接口只声明调用方用到的方法（接口隔离）。
- 选择具体实现用**工厂函数**（`build_ocr_engine(settings)`），集中在应用装配处，不散落在业务代码里。
- 测试替身用 **Fake**：一个真实可运行的简化实现（`FakeOcrEngine`），**不使用 mock 打补丁**。

### 4.3 继承

- 继承只用于两处：① 错误体系（`AppError` 及其子类，层级不超过 2 层）；② 框架要求的基类（`DeclarativeBase`、`pydantic.BaseModel`）。
- 其他场景**用组合代替继承**：需要复用行为，就把它做成被注入的对象。
- **禁止**多重继承。**禁止**为了复用几行代码而建立基类。

### 4.4 数据对象

| 类别 | 用什么 | 规则 |
| :--- | :--- | :--- |
| 接口请求/响应 | Pydantic `BaseModel` | 只描述数据和校验，不写业务逻辑 |
| 层间传递的值（如 OCR 结果） | `@dataclass(frozen=True)` | 不可变，创建后不得修改 |
| 数据库表 | SQLAlchemy ORM 模型 | 只描述表结构和关系，不写业务规则 |

三类对象不得混用：不把 ORM 模型直接返回给前端，不把 Pydantic 模型写入数据库。

### 4.5 封装

- 以下划线开头的属性和方法是私有的，类外**禁止**访问。
- 对外只暴露方法，不暴露内部集合或会话。需要返回集合时返回副本或不可变类型。
- 构造函数里**禁止**做耗时或有副作用的操作（读文件、加载模型、连接外部服务）；这类初始化延迟到第一次使用时（如 `RapidOcrEngine` 首次识别时才加载模型）。

### 4.6 SOLID 对照

| 原则 | 在本项目的体现 |
| :--- | :--- |
| 单一职责 | 一个类只有一个变化原因：`ImageService` 管图片存取，`UploadService` 编排上传流程，路由只做协议转换 |
| 开闭 | 新增 OCR 引擎不修改 service |
| 里氏替换 | 所有 `OcrEngine` 实现可互换，行为契约一致 |
| 接口隔离 | `Protocol` 只含调用方用到的方法 |
| 依赖倒置 | service 依赖 `OcrEngine` 接口，不依赖 RapidOCR |

### 4.7 禁止项

- **禁止**"万能工具类"：名为 `Utils`、`Helper`、`Common` 的类或只含静态方法的类。无状态的函数就写成模块级函数。
- **禁止**用类变量保存可变的共享状态。
- **禁止**为只有一个实现、也不会有第二个实现的东西提前抽接口。出现第二个实现或测试需要替身时再抽。

### 4.8 本项目采用的设计模式

| 模式 | 位置 | 作用 |
| :--- | :--- | :--- |
| 适配器 | `OcrEngine` 与各实现 | 屏蔽不同 OCR 库的差异 |
| 策略 | 运行时选择 OCR 引擎 | 同一接口，行为可替换 |
| 工厂函数 | `build_ocr_engine` | 集中创建具体引擎 |
| 依赖注入 | service 构造函数、FastAPI `Depends` | 解耦并便于测试 |
| 异常层次 | `AppError` 子类 | 用类型表达错误，统一转换成响应 |

新增设计模式前先更新本表。

## 5. 文件上传与安全

- 按文件**内容**判断类型（用 Pillow 打开验证），不信任扩展名和 `Content-Type`。
- 允许 JPEG、PNG、WebP；大小上限由 `MAX_UPLOAD_MB` 配置，默认 10。
- 存盘文件名由服务端生成（UUID），**禁止**使用用户提供的文件名。
- 读取图片前必须校验 `image_id` 匹配 `^[0-9a-f]{32}$`，防止路径穿越。
- CORS 只在开发环境放开，来源写在配置里。

## 6. 测试规范（TDD）

- 开发遵循 `.claude/skills/test-driven-development`：**没有先失败的测试，就不写生产代码**。
- 测试目录与代码对应：`app/services/mistakes.py` ↔ `tests/test_mistakes_service.py`；接口 ↔ `tests/api/test_*.py`。
- 测试名描述行为：`test_create_mistake_without_content_returns_422`，不要 `test_1`。
- 一个测试只验证一个行为。同一行为的多种输入用 `@pytest.mark.parametrize`。
- 每个接口至少有成功、失败、边界三类测试。PRD 的每条验收标准至少对应一个测试。
- **接口测试必须断言完整响应**：HTTP 状态码、`code` 与状态码相等、`message`、`data` 的结构，而不是只看状态码。
- 测试必须确定、快速、独立：每个用例用独立的临时 SQLite 和临时目录；不联网；不依赖执行顺序；时间通过注入的时钟固定。
- 默认 OCR 使用 `FakeOcrEngine`。真实 RapidOCR 的测试标 `@pytest.mark.integration`，默认不跑。
- 被跳过的测试不算通过，也不算失败；汇报时必须说明。
- 提交前必须全部通过：

```bash
cd backend && uv run ruff check . && uv run ruff format --check . && uv run pytest -m "not integration"
```

## 7. 前端规范

- 必须使用 TypeScript，开启 `strict`。
- 所有网络请求只能通过 `src/api/` 里的封装发出；页面和组件**禁止**直接调用 `fetch`。
- 封装层统一处理响应结构：`code` 为 2xx 时返回 `data`，否则抛出 `ApiError(code, message, data)`。页面只处理 `ApiError`，直接展示 `message`。
- 网络失败（断网、超时）也转成 `ApiError`，`code` 为 0，`message` 为"网络连接失败，请检查网络"。
- 所有会等待的操作（上传、OCR、保存）必须有加载态，并在等待期间禁用重复提交。
- 所有失败必须让用户看到提示，禁止只写 `console.error`。
- 移动端优先：先保证 375px 宽度可用，再适配桌面；可点击元素不小于 44px。
- 手机拍照使用 `<input type="file" accept="image/*" capture>`。
- 组件测试覆盖：必填校验、OCR 失败降级、列表渲染、错误提示。

## 8. Git 与协作规范

- **`main` 已开启分支保护**：协作者必须通过合并请求合并，且 CI 的后端、前端两项检查必须全绿；禁止强推和删除。管理员可绕过，仅用于合并迭代分支、打标签、紧急修复。设置详情见 `docs/PROGRESS.md`「怎么分工」。
- 主分支 `main` 保持可运行。功能在分支上做，分支名 `feat/<主题>`、`fix/<主题>`、`docs/<主题>`，完成后合并。
- 提交信息格式：`<类型>: <中文说明>`，类型为 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`。例：`feat: 上传图片并返回 OCR 草稿`。
- 一次提交只做一件事；测试和对应的实现可以在同一次提交里。
- 不提交：`data/`、数据库文件、`.venv/`、`node_modules/`、个人本地配置、任何密钥。
- 文档和代码一起改：接口、数据模型、规范变动时，同一次提交里更新 `docs/`。

## 9. 工作流程（Spec 驱动）

**没有规格、计划、任务，就不写代码**（宪法原则 VI）。每个迭代按下面的顺序，不跳步：

1. **规格**（`/speckit-specify`）：对照 PRD 确定本迭代范围（只承诺 P0），写清楚做什么、为什么、怎么算做完；不写技术实现。产物 `specs/<序号>-<名称>/spec.md`。
2. **计划**（`/speckit-plan`）：定接口、数据模型、风险，并做宪法检查。产物 `plan.md`、`research.md`、`data-model.md`、`contracts/`、`quickstart.md`。
3. **任务**（`/speckit-tasks`）：拆成可认领的任务，每个任务是一个 TDD 循环。产物 `tasks.md`。
4. **认领任务**（多人协作）：开工前在 `tasks.md` 的任务编号后写 `@姓名`，单独提交并推送；一个任务只能有一个负责人。详见 `docs/PROGRESS.md`「怎么分工」。
5. **实现**（`/speckit-implement`）：按任务逐个做，红 → 绿 → 重构；做完把 `tasks.md` 里的 `- [ ]` 改成 `- [x]`，**与代码同一次提交**。
6. **验收**：全部测试通过后，按 `quickstart.md` 在浏览器里手动走一遍，对照规格的验收场景。
7. **收尾**：更新文档（接口、数据模型、`docs/PROGRESS.md` 总表），合并分支，打版本标签 `v0.<迭代号>`。`tools/progress.sh` 可随时查看统计。

**需要先改规格的情况**：新增规格里没有的功能，或改变已有功能的行为。范围之外的想法记在 PRD 的后续迭代方向或风险表里，不在当前迭代顺手实现。
**不需要新规格的情况**：修复已有功能的 bug（必须先写能复现它的失败测试）、文档笔误、纯样式微调。
