# Research: 迭代 2 的关键决定

每项决定都记录被否决的方案，避免日后重复讨论。

## D1：删除标签不改表结构，靠事务内先删关联行

- **事实**：`mistake_tag.tag_id` 的外键没有 `ON DELETE CASCADE`，而用户机器上已有的数据库就是这样建的（已用 `sqlite_master` 核实）。
- **决定**：`TagService.delete` 在同一个事务里先 `DELETE FROM mistake_tag WHERE tag_id = ?`，再删标签。
- **否决**：给外键加 `ON DELETE CASCADE`。`create_all` 不会修改已存在的表，已有用户的库不会生效，必须引入 Alembic 并写迁移，成本与风险都高于收益。
- **后果**：本迭代没有表结构变更，因此没有业务迁移脚本。（数据库版本化的基线见 D10。）

## D2：关键字搜索 = 转义后的"包含"匹配，范围三个字段

- **决定**：在 `content`、`answer`、`error_reason` 三个字段上做不区分英文大小写的包含匹配，用 SQLAlchemy 的 `contains(..., autoescape=True)`，使 `%`、`_` 按普通字符处理；首尾空格去掉，全空白等同于没有关键字。
- **否决**：①全文索引（FTS5）：几百道题用不上，且需要改表；②分词或拼音容错：规格明确不做；③自己拼 `LIKE '%…%'` 字符串：有通配符与注入风险。
- **性能**：全表扫描，千级数据在 SQLite 上远低于 1 秒（SC-003）。数据量真的增长后再加索引或 FTS。

## D3：多个标签筛选取交集

- **决定**：对每个所选标签各加一个"错题带有该标签"的条件，条件之间取"且"。
- **否决**：并集（任一标签）。复习时通常是逐步缩小范围，交集更符合；规格 Assumptions 已记录，用户已确认。

## D4：掌握程度用 `PUT /api/mistakes/{id}/mastery`（2026-10-27 修订，取代原布尔设计）

- **决定**（2026-10-03，已被取代）：请求体 `{"mastered": true|false}`，幂等。
- **修订**（2026-10-27，依据老师"掌握程度分级管理"要求与 PRD v0.2）：改为请求体 `{"level": 1|2|3|4|5}`，幂等，返回更新后的完整错题。达到四级写 `mastered_at`，降级清空（见 D12）。
- **否决**：继续用布尔 + 另加等级字段。两个字段表达同一件事，必然出现"已掌握但一级"之类的矛盾状态。

## D5：筛选条件放在页面地址（查询参数）

- **决定**：`?subject=2&tag=函数&tag=易错&status=todo&q=配方`；用 `router.replace` 更新，不产生多余的历史记录。刷新、前进后退、从详情返回都能还原（FR-009）。
- **否决**：①组件内的临时状态：刷新和返回都会丢；②`localStorage`：规格明确不要求关闭应用后仍记住，且会引入"悄悄带着旧条件"的困惑。

## D6：标记不做乐观更新

- **决定**：点击后等服务端返回再更新界面，按钮在等待期间显示忙碌并禁用。失败时界面保持原状态并提示（FR-015）。
- **否决**：乐观更新再回滚。单机本地服务响应在毫秒级，等待感知不到；乐观更新要处理回滚与并发，更容易出现"界面说已掌握、其实没保存"。

## D7：后端对未知的筛选条件返回空结果，前端负责清理

- **决定**：`subject_id`、`tag` 指向不存在的值时，后端照常返回 200 与空列表；前端加载学科与标签列表后，剔除不存在的条件并提示（FR-010）。
- **否决**：后端对未知条件返回 422。这会让一个过期的书签地址直接变成报错页，违背"不能报错"。

## D8：学科列表带 `mistake_count`，新增标签列表接口

- **决定**：`GET /api/subjects` 每项增加 `mistake_count`；新增 `GET /api/tags` 返回 `{id, name, mistake_count}`，按名称排序，包含 0 次使用的标签。一次查询用 `LEFT JOIN … GROUP BY` 算出，避免逐条查询。
- **理由**：管理页要显示使用数（FR-024）；筛选栏要有标签可选（FR-011）。都是向后兼容的新增字段。

## D9：被占用学科拒绝删除，返回 409 并带数量

- **决定**：`DELETE /api/subjects/{id}`，学科下有错题时返回 409，`message` 为"该学科下还有 N 道错题，请先处理这些错题"，`data` 为 `{"mistake_count": N}`。
- **否决**：自动转移到"未分类"：引入一个新的特殊学科，规格明确不做。

## D10：数据库版本化——引入 Alembic，基线 `0001`

- **背景**：宪法 v1.1.0 规定表结构变更必须有版本。迭代 1 的库是 `create_all` 建的，**没有版本记录**，无法分辨它是哪一版结构。
- **决定**：引入 Alembic；基线迁移 `0001` 等于迭代 1 的表结构。应用启动时：
  - 库没有版本记录 → 登记为 `0001`（不改任何数据）；
  - 库版本低于代码 → 自动升级到最新；
  - 库版本高于代码 → 拒绝启动并说明原因（例如回退了代码）。
- **测试**：①新库启动后版本是最新；②用 `create_all` 建的旧库（带数据）启动后被登记为 `0001` 且数据不丢；③版本比代码新时拒绝启动；④升级到最新后的结构与 ORM 模型一致（改了模型忘写迁移，测试会失败）。
- **为什么现在就做**：越晚登记基线，越难确认旧库的真实结构；现在登记成本最低。
- **否决**：①自己在库里建一张 `schema_version` 表并手写升级逻辑：重复造轮子，没有「自动生成差异」和成熟的升级链；②等到第一次改表时再引入：那时才发现旧库没有版本，登记基线要在改表的同时做，风险叠加。
- **范围说明**：这是对宪法新规则的落实，不是新功能；对应任务 T047–T050。若项目负责人希望推迟，必须先修订宪法。

## D11：掌握程度五级化——改表走迁移 `0002`，存量 `mastered` 映射为等级

- **背景**：老师"错题管理"模块要求掌握程度分五级（一~五级）、记录什么时候掌握。原迭代 2 设计是布尔 `mastered`，与本迭代"表结构不变"的结论冲突。
- **决定**：`mistake.mastered` BOOL 改为 `mastery_level` INTEGER NOT NULL DEFAULT 1，新增 `mastered_at` DATETIME NULL；变更经 Alembic 迁移 `0002` 落地（基线 `0001` 先行登记）。存量映射：`mastered=true → 4`、`false → 1`，`mastered_at = NULL`（旧数据没记录过掌握时间）。
- **为什么 true→4 而不是 5**：旧的"已掌握"更接近"可以清理了"，与清理门槛（四级）一致；映射成 5 会让一批题未经自评直接"完全掌握"。
- **时机**：迭代 2 代码 0 开始，现在改规格零返工成本。
- **否决**：①保留 BOOL 再加 `mastery_level` 两列并存：两个字段表达同一语义，必然矛盾；②新表存等级、BOOL 列不动：同样双写不一致；③不改表，等级存标签：标签是自由文本，无法做区间筛选与门槛校验。

## D12：掌握时间的语义——达四级记录、降级清空、再达重记

- **决定**：`mastered_at` 写入时机：旧等级 <4 且新等级 ≥4 → 写入当前时刻（注入时钟，UTC）；新等级 <4 → 置 NULL；等级不变 → 不动（幂等）。降级再升回，按升回时刻重新记录。
- **为什么选四级**：与清理门槛同线，"熟练掌握"才谈得上"什么时候掌握的"；用户长期停在四级也能看到掌握时间（若设为五级才记录，多数人永远看不到）。
- **否决**：①每次调级都刷新："什么时候掌握"语义模糊；②只在首次达到四级记录、降级不清空：降级后仍显示掌握时间，与等级展示矛盾（FR-015）。

## D13：清理=手动删除 + 四级门槛 + 二次确认，不设回收站与自动清理

- **决定**：`DELETE /api/mistakes/{id}`，等级 <4 返回 409，`message` 提示当前等级，`data` 为 `{"mastery_level": N}`（沿用 D9 学科占用的拒绝模式）；≥4 删除成功，关联行由 `mistake_tag.mistake_id` 的外键级联清理。前端删除前二次确认。不删除原图文件（与迭代 1 孤儿图片策略一致）。
- **否决**：①自动清理（到四级自动删）：违反宪法 V"破坏性操作必须用户确认"；②回收站：单机个人应用，二次确认 + 门槛已防误删，复杂度不值；③无门槛删除：老师明确要求"熟练度到了一定程度才允许清理"。

## D14：容量提醒=软提醒，总数经 `overall_total` 下发

- **决定**：`GET /api/mistakes` 响应增加 `overall_total`（不受筛选影响的总数，一次 COUNT 即可）；前端在总数 > 100 时于列表页顶部显示提醒横幅，回到 100 以内消失。阈值 100 为常量（老师建议容量 100 以内、上限 200）。
- **否决**：①硬上限（到 200 阻止录入）：老师口径是"建议"，阻止录入违背"失败不阻断"精神，且软提醒已能引导清理；②单独统计接口：列表页本来就要拉数据，多一个请求没必要；③用筛选后的 `total` 判断：用户筛到 3 道题时提醒会消失，提醒应反映本子真实总量。

## D15：取消 500 题性能抽测

- **决定**：删除原 SC-001（500 题 10 秒内找到）与 T052 性能抽测。容量目标改为 100 题以内（上限约 200），SQLite 全表扫描在千级数据也远低于 1 秒（D2 已有结论），专门的性能验收场景失去意义；保留 SC-002（界面反馈 1 秒内）。
- **后续**：数据量显著增长（如接入多用户）再按 research D2 的预留评估索引或 FTS。


## D16：孤儿标签自动清理（2026-10-27 用户要求）

- **背景**：用户提出"删除错题后应做可达性分析，把没人引用的标签直接删除"。原设计（spec v2 之前）是无引用标签保留在管理页，靠用户手动清理。
- **决定**：`MistakeService.delete` 与 `MistakeService.update`（编辑换标签可能使旧标签失去全部引用）在同一事务里删除 `NOT IN (SELECT tag_id FROM mistake_tag)` 的标签。
- **连带调整**：US3/US4 验收场景、FR-021/FR-024、边界与假设同步更新；`GET /api/tags` 仍返回 0 使用标签（保留行为，实际很少出现）。
- **否决**：①只删题不清理（用户明确要求清理）；②管理页提供"清理全部空标签"按钮（不如自动清理及时，且多一个入口）；③连"手动删标签"也改为级联删题（违反宪法 V，错题不可因标签操作丢失）。
